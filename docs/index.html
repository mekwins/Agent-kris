🧠 Brain

A personal AI second brain — many self-describing vaults, one generic engine, driven through Claude.

✓ Multi-vault engine ✓ MCP Server (SSE) ✓ Compile agent ✓ Per-vault vector search ◷ GitHub sync + fly.io (next)

What is this

Brain is an AI-powered knowledge system built around markdown vaults. You can have several — e.g. work, spanish, personal — each an independent knowledge base with its own rules, its own wiki, and its own vector index. Three layers:

  • Generic engine (src/) — filesystem ops, embeddings, per-vault vector store, and the agent loop. Identical for every vault.
  • Per-vault profile (vaults/<id>/.brain/) — the description, note-type schemas, folder routing, and compile rules that make each vault behave differently. Rules are data, not code.
  • Registry (wikis.toml) — lists which vaults exist and which is the default.

Your primary interface is Claude. You talk; Claude calls brain tools, always targeting a specific vault via the wiki parameter (it calls brain_list_wikis to discover them).

Core pattern
Pick a vault → brain_write saves rough notes to that vault's inbox/ → brain_compile runs the agent → structured, cross-linked wiki pages appear (people resolved, tasks linked), inbox file moves to processed/ → brain_search/brain_recall find everything later.

Worked example

A real, executed run (full trace in example-run.md). You say to Claude, targeting the work vault:

"Add a task to send the EA onboarding pack to Kristina by Friday,
 and follow up with Ravi Ganda on Kafka Pod 1."
  1. Capture — brain_write(wiki="work") drops a note in work/inbox/.
  2. Compile — brain_compile(wiki="work") reads the vault's .brain/ profile (which defines a task type).
  3. Resolve people — Kristina is unknown → a people/kristina.md stub is created (no invented facts). Ravi Ganda already exists → his page is reused, not duplicated.
  4. Link — two tasks/*.md pages are written with typed frontmatter (status, assignee, due) and [[wikilinks]] to the people and the related project. An ## Assigned Tasks back-link is added to each person page.
  5. Index — pages are embedded into work/.vectors.json; the inbox note moves to work/processed/.

Result: brain_recall("Ravi Ganda") now returns his page and the linked follow-up task — and Obsidian shows the backlink for free. Structured output from one plain sentence, with zero code changes to add the task type.

How vaults work

Each vault is a directory under vaults/ (or an external path). The registry lists them:

# wikis.toml
default = "work"

[wikis.work]
[wikis.spanish]
[wikis.personal]

Every MCP tool takes an optional wiki id; omit it and the default is used. The AI discovers vaults with brain_list_wikis, which returns each vault's description, domains, and note types. Vaults are fully isolated: each keeps its own wiki/, inbox/, and .vectors.json, so a Spanish search never leaks into work.

Vault profiles (.brain/)

Each vault self-describes in a .brain/ folder. This is where per-vault behaviour lives — edit these, not Python.

FileFormatRead byPurpose
profile.tomlTOMLcode + agentDescription, domains, and note-type schemas (the structured bits the program iterates over)
compile.mdMarkdowncompile agentThis vault's editorial rules / voice
folders.mdMarkdowncompile agentFolder routing — where each kind of note goes

Why TOML for one file? Because the code reads profile.toml programmatically (for brain_list_wikis and to inject note-type schemas into the compile prompt), so it needs reliable structure. compile.md/folders.md are prose only the LLM reads, so markdown is friendlier.

# vaults/work/.brain/profile.toml (excerpt)
description = "Work: Nexteer, EA, AI strategy, projects and the people involved."
domains = ["projects", "people", "concepts", "areas", "brainstorm"]

[types.task]
frontmatter = ["title", "status", "assignee", "due", "related", "tags"]
hint = "Actionable to-do. Resolve the assignee to an existing [[person]] or create a stub, link the related [[project]]."

Adding a vault

  1. Create the folder: vaults/<id>/.brain/ plus inbox/ wiki/ processed/ sources/.
  2. Write .brain/profile.toml (description, domains, note types), compile.md, and folders.md.
  3. Add [wikis.<id>] to wikis.toml.
  4. Done — brain_list_wikis now advertises it and every tool accepts wiki="<id>". No code change.
Universal capabilities live in the engine
Tasks + people cross-referencing is defined once in the shared compile prompt, so every vault (present and future) supports it automatically. Vault-specific taxonomy stays in the profile.

EMBEDDING_API_KEY=<azure-openai-key>

# Azure AI Foundry — compile agent (Claude Sonnet)

ANTHROPIC_FOUNDRY_API_KEY=<foundry-key>

# Multi-vault
VAULTS_ROOT=./vaults
WIKIS_CONFIG=./wikis.toml
DEFAULT_WIKI=work

# MCP server API key — required for remote (non-localhost) connections
MCP_API_KEY=<strong-random-key>
Keep .env out of git
.env is gitignored. Generate MCP_API_KEY with python3 -c "import secrets; print(secrets.token_urlsafe(32))"

Connect to Claude Desktop

Claude Desktop connects through mcp-remote, which bridges stdio to HTTP SSE. Edit ~/Library/Application Support/Claude/claude_desktop_config.json:

{
  "mcpServers": {
    "brain": {
      "command": "npx",
      "args": [
        "mcp-remote",
        "http://127.0.0.1:8765/sse",
        "--header",
        "x-api-key:<your-MCP_API_KEY>"
      ]
    }
  }
}
Moving to remote hosting
When you deploy to fly.io, change only the URL: http://127.0.0.1:8765/sse → https://<app>.fly.dev/sse. The API key header stays the same.

MCP Tools

Ask Claude in natural language — it picks the tool and the target wiki. Every tool below (except brain_list_wikis) accepts an optional wiki id.

brain_list_wikis
List available vaults with their descriptions, domains, and note types. Called first so the AI knows which wiki to target.
— no params —
brain_write
Capture anything to a vault's inbox/ and auto-embed for search.
contenttags domaintitle source_urlwiki
brain_compile
Run the compile agent against a vault. inbox → wiki pages, moves to processed/, updates index/log.
task: compile inbox | compile sources | lint | search limitquerywiki
brain_search
Hybrid semantic + keyword search inside a vault.
queryscope mode: hybrid | semantic | keyword limitwiki
brain_recall
Fetch a wiki page and its wikilinked neighbors.
topicdepth: 1 | 2wiki
brain_context
Recent pages for session priming. Optional agent_type filters by a domain within the vault.
agent_typewiki
brain_relate
Shared tags and shortest wikilink path between two concepts.
concept_aconcept_bwiki
brain_clip
Clip a web URL to a vault's inbox (article markdown + downloaded images).
urldomaintagswiki

Compile agent

Triggered via brain_compile. It's an agentic loop (Claude via Azure Foundry) with its own filesystem tools, scoped to one vault. Its system prompt = generic engine mechanics + that vault's .brain/compile.md + its note-type schemas.

  1. Reads the vault's .brain/folders.md routing rules
  2. Lists inbox/ files with status: inbox
  3. Classifies each, searches existing wiki for wikilink targets
  4. Writes structured pages to the right folder (per folders.md)
  5. Embeds each page into the vault's vector store
  6. Moves the inbox file to processed/
  7. Updates wiki/index.md and wiki/log.md

Tasks & people

Tasks are a universal capability — supported in every vault. When a note describes something to do, the compile agent:

  • Creates a page in wiki/tasks/ with frontmatter status, assignee, due, related.
  • Resolves each named person before writing: searches the wiki first — links an existing people/ page if found (no duplicate), or creates a short stub if not.
  • Links the task to related projects/concepts, and adds an ## Assigned Tasks back-link on the person's page (bidirectional).

See the worked example for a real trace of this behaviour.

Search & recall

ModeHow it worksBest for
hybrid (default)Semantic + keyword mergedMost queries
semanticCosine similarity on embeddingsConcept queries

All search is per-vault: pass wiki to choose which knowledge base to search. scope further filters by a domain string within that vault.

Vault structure

vaults/<id>/ ├── .brain/ ← this vault's profile │ ├── profile.toml ← description, domains, note-type schemas │ ├── compile.md ← editorial rules for this vault │ └── folders.md ← folder routing ├── inbox/ ← uncompiled captures (append-only) ├── processed/ ← archive of compiled raw notes ├── wiki/ ← compiled, interlinked knowledge base │ ├── index.md · log.md │ ├── concepts/ people/ projects/ │ ├── tasks/ areas/ brainstorm/ learning/ ├── sources/ ← immutable raw imports └── .vectors.json ← per-vault embedding store (gitignored)

Which folders a vault actually uses comes from its own .brain/folders.md — e.g. spanish is mostly learning/, while work leans on projects/, people/, and tasks/.

Frontmatter schema

---
title: "Page Title"
date: 2026-07-05
domain: <a domain string valid for this vault>
tags: [tag1, tag2]
status: active            # inbox notes use status: inbox
---

Note-type–specific fields (e.g. a task's assignee/due) are declared per vault in .brain/profile.toml and applied by the compile agent.

Wikilinks

Pages link with [[Page Title]]. The compile agent searches for existing pages before writing so links are woven in automatically.

  • Link targets match the title of an existing wiki page in the same vault.
  • Broken links are reported by the lint task.
  • brain_recall follows wikilinks; brain_relate finds shortest paths.
  • Because links are markdown, Obsidian's backlinks/graph work with zero extra setup.

Deploy on fly.io

The repo ships a Dockerfile, fly.toml, and docker-entrypoint.sh. The server binds 0.0.0.0 and reads PORT from the platform; vaults live on a persistent volume.

# 1. register the app
fly launch --no-deploy --copy-config --name kris-brain-mcp

# 2. persistent volume for the vaults + vector stores (single machine)
fly volumes create brain_data --size 1 --region iad

# 3. secrets (from your .env)
fly secrets set EMBEDDING_ENDPOINT="..." EMBEDDING_API_KEY="..." \
  ANTHROPIC_FOUNDRY_BASE_URL="..." ANTHROPIC_FOUNDRY_API_KEY="..." \
  MCP_API_KEY="$(openssl rand -hex 24)"

# 4. ship it
fly deploy
One volume = one machine
Vaults and their vector stores live on a single fly volume. Keep it to one machine; don't scale horizontally without moving to shared storage. Set MCP_API_KEY — without it the endpoint is public.

Troubleshooting

Brain tools not showing in Claude Desktop

  • Verify the server: curl -o /dev/null -w "%{http_code}" http://127.0.0.1:8765/sse --max-time 2 → 200
  • Verify the x-api-key in Claude config matches MCP_API_KEY.
  • Restart Claude Desktop after config changes (Cmd+Q).

"Unknown wiki" error

The wiki id isn't in wikis.toml, or its folder is missing. Run brain_list_wikis (or check wikis.toml) for valid ids.

Search returns no results

That vault's index may be empty/stale. Rebuild: uv run python scripts/index_vault.py --wiki <id>. Keyword mode works without the index.

Missing env var on startup

Required: EMBEDDING_ENDPOINT, EMBEDDING_API_KEY, ANTHROPIC_FOUNDRY_BASE_URL, ANTHROPIC_FOUNDRY_API_KEY. For remote, also MCP_API_KEY.

Compile agent fails or stalls

  • Check Azure AI Foundry quota/endpoint.
  • The agent has a 50-iteration cap — for large batches use limit=5.
